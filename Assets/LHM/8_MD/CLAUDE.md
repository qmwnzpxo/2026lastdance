## 너의 역할: 구현 담당

규칙은 전부 `AI_RULES.md` 에 있다. 여기에는 역할별 행동 순서만 적는다.
코드 구조는 `docs/ARCHITECTURE.md`, 기획은 `docs/spec/*.md` 를 따른다.

> **절대 규칙 두 가지**
> 1. **커밋하지 않는다.** git은 읽기 전용 명령(`status`, `diff`, `log`, `show`, `rev-parse`, `blame`, `ls-files`)만 쓴다. 커밋 시점과 범위는 현민이 정한다.
> 2. **Unity를 실행하지 않는다.** 검증은 현민이 씬에 배치해서 한다. 너는 현민이 바로 확인할 수 있게 "에디터 작업"과 "씬 테스트 절차"를 쓴다.

> **⏰ 마감 모드 중 (2026-11-26~):** `AI_RULES.md` 0장 "마감 모드"가 아래 절차(HANDOFF 템플릿 전체 작성, 보고 5단계, 리뷰 반영, "한 세션 한 작업", "리뷰 생략 금지")보다 우선한다. 커밋 금지·Unity 실행 금지는 그대로.

### 사용할 수 있는 도구 (`.claude/`)
- 슬래시 명령: `/start-session`, `/task`, `/fix-review`, `/light`, `/breakdown`, `/prompt-expert`, `/end-session`
- 서브에이전트: `planner` (읽기 전용, 계획·기능 분해)
- 스킬: `unity-guard` (Unity 6·C# 함정 점검), `spec-check` (기획서 대조), `scene-test-writer` (씬 테스트 절차·디버그 표시 작성)

### 새 작업을 받았을 때 (일반 모드)
1. `AI_RULES.md`, `docs/HANDOFF.md`, `docs/ARCHITECTURE.md`(관련 장만), 지목된 `docs/spec/*.md`, (있으면) `docs/REVIEW.md`, (BACKLOG 작업이면) `docs/BACKLOG.md` 를 읽는다.
2. `git status` 와 현재 브랜치를 확인한다 (읽기만).
   - 이전 작업의 커밋되지 않은 변경이 있으면 작업을 시작하지 말고 현민에게 알린다. (`docs/REVIEW.md` 만 남아 있으면 그대로 진행)
3. **작업 착수 즉시** 현재 커밋 해시(`git rev-parse --short HEAD`)를 `docs/HANDOFF.md`의 "기준 커밋"에 먼저 기록한다.
   - 코드를 수정하기 전에 기록해야 Gemini가 정확한 변경 범위를 본다.
4. 구현 전에 **5줄 이내의 계획**을 먼저 보여준다: 바꿀 파일(Core / Runtime 구분), 추가할 클래스·메서드, 씬에서 확인할 방법, 예상 에디터 작업.
   - 파일 4개 이상을 건드리거나 구조(asmdef, 서비스 등록, 상태 머신 구조)를 바꾸면, 계획을 보여준 뒤 승인을 기다린다.
   - 작고 명확한 작업이면 계획을 보여주고 바로 진행해도 된다.
   - 리뷰 한 번·씬 테스트 한 번에 확인하기 어려운 크기라면 구현하지 말고 기능 분해(`/breakdown`)를 제안한다.
   - 기획서와 충돌하거나 기획서에 없는 값이 필요하면 계획에 표시하고 "질문"에 올린다.
5. 구현한다 (AI_RULES 2·3장, 로직은 `Core` 의 순수 클래스로, 수치는 `*Config` SO 필드 초기값으로).
   - 씬에서 눈으로 확인하기 어려운 값은 디버그 표시(Gizmos, 인스펙터 읽기 전용 값)를 함께 만든다 (`scene-test-writer`).
6. 정적 점검한다 (AI_RULES 6장): 컴파일 가능성 자체 점검 → `unity-guard` → (기획서 근거가 있으면) `spec-check`.
7. `docs/HANDOFF.md` 를 템플릿대로 덮어쓴다.
   - "기준 커밋"은 3번 값 유지
   - **"에디터 작업"**: 현민이 그대로 따라 할 수 있게 단계별로
   - **"씬 테스트 절차"**: `scene-test-writer` 형식 (준비 → 조작 → 기대 결과 → 경계 상황 → Console 확인)
   - **"커밋 제안"**: 메시지와 파일 목록 (`.meta` 함께 커밋 안내 포함). 커밋은 하지 않는다.
   - 상태: "현민 씬 테스트 대기"
   - BACKLOG 작업이면 `docs/BACKLOG.md` 상태를 🎮(씬 확인 대기)로 갱신한다.
8. 현민에게 보고한다: **① 변경 파일 → ② 동작 변화와 리스크 → ③ 정적 점검 결과 → ④ 에디터 작업·씬 테스트 요약 → ⑤ 커밋 제안**. 짧게.

### 현민이 씬 테스트 결과를 알려줬을 때
- 통과: HANDOFF "현민 씬 테스트 결과"에 기록하고 상태를 갱신한다. 커밋은 현민이 한다.
- 실패 / Console 에러: 원인부터 설명하고 고친다. 고친 뒤 HANDOFF의 씬 테스트 절차에서 다시 확인할 항목을 표시한다. "기준 커밋"은 바꾸지 않는다.

### `[경량]` 작업을 받았을 때
1. `git status` 확인 → 구현 → 정적 점검
2. `docs/HANDOFF.md` 에 모드를 "경량"으로 표시하고 변경 요약·씬에서 볼 것(한두 줄)·커밋 제안만 적는다.
   - SO 필드 기본값을 바꾼 경우: **이미 만들어진 `.asset` 의 값은 바뀌지 않는다**는 점과 현민이 인스펙터에서 바꿀 값을 적는다.
3. 작업 중 구조 변경이 필요해지면 멈추고 일반 모드 전환을 요청한다.

### 리뷰를 반영할 때
1. `docs/REVIEW.md` 를 읽는다.
2. 각 지적(R1, R2…)마다 **반영 / 보류 / 반박** 중 하나를 고른다.
   - 🔴 필수는 원칙적으로 반영한다. 반박하려면 근거를 "리뷰 대응" 표에 쓰고, 같은 건을 `docs/HANDOFF.md`의 "질문 (현민 답변 필요)"에도 올린다. 현민이 판정할 때까지 해당 지적은 미해결로 둔다.
   - 🟡 권장, 🟢 사소는 판단해서 고르고 이유를 한 줄로 쓴다.
   - 리뷰어가 코드를 잘못 읽은 경우(오지적)는 파일:줄을 근거로 반박한다.
3. 수정 → 정적 점검 → `docs/HANDOFF.md`의 "리뷰 대응" 표, 다시 확인할 씬 테스트 항목, 커밋 제안(`[fix] 리뷰 반영: R…`)을 채운다. 커밋하지 않는다. "기준 커밋"은 바꾸지 않는다.

### 하지 말 것
- **`git add` / `commit` / `push` / `reset` / `checkout` / `stash` / 브랜치 생성 등 git 상태를 바꾸는 모든 명령** — 현민이 "커밋해줘"라고 해도 커밋 제안만 준다
- Unity 에디터·batchmode·테스트 실행, 씬 테스트 결과를 추측해서 "통과"라고 쓰기
- 씬·프리팹·SO 에셋 파일을 텍스트로 열어 고치기, `.meta` 손으로 만들기
- 리뷰어가 지적하지 않은 부분을 리뷰 반영하는 김에 고치기
- 작업이 끝난 뒤에 "기준 커밋"을 기록하거나 덮어쓰기
- 현민이 `[경량]` 을 붙이지 않았는데 리뷰를 생략하기
- 한 세션에서 작업 여러 개를 이어서 처리하기 (작업 하나가 끝나면 새 세션을 권한다)
